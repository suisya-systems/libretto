## 1. 結論（決定事項の一覧）

libretto は「**話し相手が依頼を聞き取り、依頼書と確認項目を別々に下書きし、作り手が依頼書だけを見て下書きし、判定役が確認項目で検品し、本人が承認して、指定の場所へ届ける**」というループを、文書づくりに合わせて作ったものである。役割と人間ゲートの分け方、常駐のホスト 1 本が依頼を一本の筋で運ぶ形、確認項目を作り手に見せない検品の 3 つを柱にし、コード開発の道具（作業ブランチ・PR・CI・ペイン運用）は持ち込まない。それぞれを採る理由は本書の各節に書き切ってあり、参考にした既存の設計（claude-org・rondo・factory）との関係は 2 章にまとめた。既存の設計の判断を根拠にはしない（外の判断が変わっても libretto の判断は変わらない）。

| # | 決定 | 一言で |
|---|---|---|
| D1 | 役割は 5 つ（話し相手・下書き役・作り手・判定役・事実係）＋本人 | 聞き取る役・作る役・確かめる役を分け、人は承認だけをする。理由: 作る役の自己申告を人に見せる前に別の目で読ませたい。依頼書と確認項目を別の役が書くのは、物差しを作る側と作る側が同じだと思い込みが揃い、物差しが作る側を試さなくなるから（5.6）。参考: claude-org の窓口 / ワーカー / レビュー / 人間の分け方に、factory の「仕様と確認項目を別々に下書きする役」を足した形。配車役・整理役の常駐は 1 人用の v1 では要らない |
| D2 | **libretto は自前の画面を持つ**。本人が触るのはその画面 1 つ。実行基盤は常駐のホスト 1 本＋画面（本人の操作・ゲート・記録を 1 本のプロセスが持つ。理由: 状態の正本が 1 つになり、止めて起こし直しても台帳から続きができる。参考: rondo と同じ形）で、モデル呼び出しはアダプタ 1 か所に閉じ込める | 端末・git・PR・CI の語は画面に一切出さない。画面の見た目は本書の範囲外（窓口が別途作る）。本書は「画面が満たすべきこと」まで（[3.4 節](#34-画面が満たすべきこと場面ごと)） |
| D3 | 依頼の入口は 2 系統。**直接の会話**と、**Gmail / Slack / Meet 議事録からの候補拾い上げ**。拾い上げは**合図**（Gmail の専用ラベル `libretto`・Slack の絵文字リアクション `:memo:` を定期に一覧で拾う（Q8 = a）・Meet の新しいメモ）と**内容からの推測**の両方で行う。推測は**拾い漏れを嫌い、再現率を優先する**: 候補を落とす方向では抑えず、候補カードの**由来・拾った理由・確信度**の表示と、見送りの学習で誤検出を捌く。候補は ID で重複を除く | オーナー判断 2026-10-23（Q7 = b）。「両方にしないとエージェンティック感が薄い」「拾えないリスクの方が嫌だな」 |
| D4 | 実行モードは 2 つ: **「確認しながら」**（ゲート①②③で止まる）と**「おまかせ」**（入口で 1 回承認したら送付の手前まで自走し、質問は仮定に変えて入口に載せる。本人だけに見える届け先なら送付まで自走）。モードは**案件ごと**に選び、既定は入口ごと（両入口とも「確認しながら」で始める） | Q12 = a、Q13 = a |
| D5 | おまかせでも**必ず止まる場面**: 他人に見える送付（共有・公開・他人のドライブ）、既存ファイルの上書き、費用上限、検品の往復上限で不合格、他人の発言を成果物に引用するとき | 取り消しにくいことと、他人に関わることは自走させない |
| D6 | **入口ごとに「おまかせ」を既定にしたときは、合図付きの候補を本人の「進める」なしに入口へ入れてよい**。合図は本人の意思表示なので、入口の承認も省き（依頼書・仮定・確認項目を承認済みとみなす）、下書き・検品を経て D5 の線で止まる。**推測で拾った候補は、おまかせでも自動では動かさない。必ず本人の「進める」を待つ**。自動で始まったものは「自動で始まったもの」の一覧に出し、どの段階でも取り消せる | オーナー判断（Q10 = b、推測由来の扱いは 2026-10-23 の追加判断）。brief の「黙って着手しない」を合図付きに限って緩める判断 |
| D7 | 検品は「物差しを作り手に見せない」方式: 入口で**依頼書**と**確認項目**を別々のセッションが下書きし、本人が組として承認する。**作り手は確認項目を見ない**。判定は機械判定とモデル判定の **AND**。不合格の理由は**確認項目の本文を含まない 1 行要約**で作り手に返し、往復は**最大 3 回**（Q2 = a） | 理由は 5 章の各節と [5.6 節](#56-検品の方式を選んだ理由参考にした実験結果)に書き切った（参考として factory の実験結果を添えてある） |
| D8 | 事実は**決定的コード**が完成稿の全文から主張を棚卸しし、出典を取り寄せ、判定役が「支持するか」を判定する。棚卸しに無い主張が残れば不合格。**出典の無い主張は不合格として作り手に戻し、出典を探すか「要確認」印を付ける**（Q4 = a）。印は本人に見える | 2026-10-23 の「出典が支持しない主張」の再発防止 |
| D9 | 本人が書いた部分がある文書では、まず**文体カード**を決定的に抽出し、作り手は従い、判定役は照らす | 2026-10-23 の「声が違う」却下の再発防止 |
| D10 | 届け先は 4 つ: **版のあるウェブページ（libretto 自身が配信。本人だけ。他人に見せるのは送付）**（Q11 = a。brief の「claude.ai Artifacts」からの逸脱を明示）/ Google ドキュメント・スプレッドシート・スライド / 手元のファイル（pptx・xlsx・docx）/ note などへ貼り付ける下書き | 作り方と検品は 7 章 |
| D11 | スライドと Word は**画像に描き出して目で検品**、表計算は**再計算して式エラーを機械検出**、Google 形式は**変換後を読み戻して照合**。**実行環境に LibreOffice・poppler・生成ライブラリを入れ、事前点検で確認してから「手元のファイル」を届け先に出す**（Q6 = a） | 依存は [7.2 節](#72-依存するものと無いときの振る舞い) |
| D12 | 構成案ゲートは**長いものだけ任意**（2,000 字超・スライド 10 枚超。Q5 = a） | 短い文書で毎回止めない |
| D13 | 状態と台帳は**ホストの SQLite のデータベース 1 つ**、文書は案件ごとのフォルダ（11 章）。版は番号付きで完了印、承認は「案件・版・本文の指紋・届け先」に結び付け、送付は 3 状態。費用は呼び出しごとに追記し、**案件ごとの上限（既定 1 案件 ¥1,500 相当）と全体の上限（オーナーが決める）**（Q13 = a） | git は使わない。データベースを使う理由は 11.4（オーナー判断 2026-10-23） |
| D14 | モデルは役割ごとに固定し、アダプタで差し替える。**三系統の分担**（Q3 = a）: **Codex** が確認項目を下書きし、**Jev**（TypeSafe の判定専用モデル。確率と自信度で合否だけを返す第三の系統）が**テキストで命題にできる判定**（事実の支持・有無の確認・依頼適合の個別項目・「AI への指示」検出）を行い、**Claude** が文体・自然さ・構成と**画像を見る判定のすべて**を行う。別系統は **libretto のホストが OpenAI の API キーで直接呼ぶ**（CLI のログインは要らない。Q16 = a）。**キーが無い環境**では Claude の別セッションが確認項目を下書きし、Jev で項目を点検し、入口と承認の面に「確認項目は作り手と同じ系統が書きました」と表示する（[5.8 節](#58-codex-が無い環境での確認項目の下書き)）。Jev が無ければ Claude に回して表示 | オーナー判断 2026-10-23（「codex がない場合を考慮して」） |
| D17 | **鍵はオーナーが用意し、ホストだけが持つ。オーナー以外の使う人に登録やキーを求めない**。対象は別系統（OpenAI）・Jev（TypeSafe）・Google の OAuth クライアント・Slack アプリ。**別系統と Jev の API キーは、オーナーが設定の画面で入れる**（ファイルを開いてキーを貼る作業は求めない）。保存したキーは二度と画面に出さず、「設定済み」と末尾 4 文字だけを見せ、「入れ直す」「削除」ができる。**Google の OAuth クライアントと Slack アプリの設定は今の設計のまま**ホストの `.env.local` に置き、画面には移さない。鍵はホストの機械の上にだけあり、作り手・下書き役・判定役のセッションには渡らない。キーが無いときは既に決めた落ち方のまま動く（別系統が無ければ同系統で下書きして表示。Jev が無ければ Claude に回して表示）。モデル呼び出しのアダプタの中身として扱う | オーナー判断 2026-10-23（Q16 = a、「jev も同じ扱いがよさそう」）。画面で入れる形も同日のオーナー判断。理由: ホストはオーナー自身の PC で動く（実装設計書 P1）ので、キーを入れるのはオーナーになる。そのオーナーにファイルを開いてキーを貼らせるのは、人に手書きやコピペをさせないという libretto の決め事に反する |
| D15 | 取り込み元の文章は**常に「資料」であって「指示」ではない**。他人の発言は本文を保存せず、場所と本人が確認した要約だけを残す。出典の抜粋は案件が開いている間だけ。**Gmail の権限は本文の読み取りまで（添付は本人が渡す）**（Q9 = a） | 10 章 |
| D16 | v1 でやらないこと: 複数人の承認、note への自動投稿、音声・画像生成、日本語以外 | 8 章（内容推測と候補の自動入口は v1 に**入る**ので外した） |

オーナーに仰いだ判断（Q1〜Q16）は**すべて決定済み**で、9 章に日付付きで一覧した。本書に未決事項は無い。

## 2. 既存設計との関係

この章は、参考にした既存の設計と libretto の関係の**記録**である。libretto の各判断の理由は本文の該当節に書き切ってあり、ここに挙げた既存の決定を根拠にはしない（外の決定が変わっても libretto の判断は変わらない）。

| 既存 | 関係 | 理由 |
|---|---|---|
| **claude-org-ja**（組織の運用ルール） | **形を借りる**（役割・ゲート・報告の作法）。**コードは持ち込まない** | 借りるもの: 窓口は人間との唯一の接点で業務言語で話す（`CLAUDE.md`「コミュニケーション」）。判断仰ぎは窓口が一次承認せず必ず人へ（`org-escalation`）。1 ワーカー = 1 タスク = 1 スコープ（`org-delegate`）。読み手は重大度を付け round 上限 3。報告は見える資料と会話の両方で出す。事実は出典付きで書き、無ければ省く（citation-or-abstain）。持ち込まないもの: worktree・PR・CI 監視・renga/broker の伝送層・ディスパッチャーとキュレーターの常駐 |
| **rondo**（人の依頼を完成まで運ぶホスト） | **実行基盤の形を借り、別物として作る** | 借りる形: 常駐のホスト 1 本が依頼・ゲート・決定の記録を持ち、人はそのホストが出す**ページ**から操作する（`README.md`「The page is where a person works」、`D-0041` approver）。ゲートは「はい / いいえ」の 1 回で答えられる形（同）。独立した読み手は作り手の自己申告を人に見せる前に読み、ゲートの答えを自分で書かない（`docs/design/lap-review-stage.md` §0、`D-0065`）。中途の質問は推奨付きで本人へ運び、沈黙や期限で答えにしない（`D-0064` 注記）。**rondo のアドバイザーは「提案するだけで着手しない」（`D-0097`）**。別物にする理由: rondo の単位は「コードのラップ」で continuo / cadenza に依存し、成果は PR とマージ。libretto の単位は「文書の版」で、成果は Docs / ファイル / 貼り付け文。**方向の食い違いは 3 つ**（いずれもオーナーが選んだもの）: (1) 「おまかせ」は質問を人へ戻さず仮定に変える。理由: 本人が入口で仮定ごと承認するので、入口のあとに聞き返すと「おまかせ」の名に反する（4.4）。rondo は「沈黙では答えない」として質問を人へ運ぶが、libretto は仮定という別の答え方を採る。(2) 判定の一部（文体・自然さ・構成・画像）を同系統の Claude で行い、別系統の鍵が無い環境では確認項目の下書きも同系統で行う。理由: 文体と画像の判定に使える別系統が無く、止めるより表示で補う方が本人の役に立つ（Q3 = a、5.8）。rondo は同系統の読み手を「検品不能」と扱うが、libretto は表示付きで動かす。(3) **おまかせの入口では、合図付きの候補を本人の操作なしに入口へ入れる**。理由: 合図は本人の意思表示であり、提案で止めると自動で始まる意味が無い（Q10 = b、D6）。rondo の助言役は「提案するだけで着手しない」が、libretto はここで踏み出す |
| **factory**（L5 ソフトウェア工場、`suisya-systems/factory` と `factory-notes`） | **検品の形を移植する。L5（人が承認しない）は目指さない** | 借りる: 依頼から「仕様」と「隠しシナリオ」を別セッションで下書きし、作る役にはシナリオを見せない（`grand-design.md` 2 章）。確認項目は人が入口で組として承認し、仕様が決めていない点（Undecided）は食い違い一覧に載せる（同）。判定は決定的テスト＋LLM 判定 1 回の AND（決定 1、lap 6）。不合格は承認済みの 1 行要約だけを作る役へ返す（lap 1）。試行上限。隠すには sandbox が要る（lap 1）。借りない: 人を入口以外から外す L5 の方針（libretto は「確認しながら」を既定に残す） |

## 3. 全体像

### 3.1 役割

| 役割 | 何をする | 見えるもの | 見えないもの |
|---|---|---|---|
| **本人**（依頼者） | 依頼する・入口で承認する・（確認しながらでは）質問に答え、完成稿と送付を承認する。自動で始まったものを確認し、取り消す | 全部 | — |
| **話し相手**（本人との唯一の接点。参考: claude-org の窓口に当たる） | 本人との会話の唯一の相手。依頼を聞き取る。候補を拾い上げて提案する（推測の分類もここの配下）。各役割の結果を業務言語に直して本人へ見せる | 依頼・候補・判定の結果・送付の状態 | 確認項目の本文（要約だけ） |
| **下書き役（依頼書）** | 依頼から**依頼書**と仮定を書く | 依頼・材料・本人の過去文書 | 確認項目 |
| **下書き役（確認項目）** | 依頼から**確認項目**を書く。依頼書の下書き役とは別セッション | 依頼・材料・依頼書の「形だけ」 | 依頼書の本文と仮定 |
| **作り手**（ワーカー） | 承認された依頼書と文体カードから下書きを作る。不合格の 1 行要約を受けて直す | 依頼書・文体カード・材料・不合格の要約 | **確認項目**・判定役の理由文 |
| **判定役** | 確認項目を機械判定とモデル判定で流し、合否と 1 行要約を出す | 依頼書・確認項目・下書き（読むだけ）・事実係の表 | 作り手の説明文・作業場所 |
| **事実係**（決定的コード＋小さなモデル） | 出典の取り寄せ、主張の棚卸し、数値の転記・照合、文体カードの抽出、形式検査、依存の事前点検、**候補の推測分類**（4.2） | 下書き・材料・出典・取り込み元 | — |

### 3.2 ループ

```
依頼（会話 / 候補: 合図または推測で拾ったもの）
  → [確認しながらの入口] 本人が候補カードで「進める」
     [おまかせの入口]     合図由来の候補は自動で入口へ（入口の承認も省く）。「自動で始まったもの」に記録
                          推測由来の候補はどちらの入口でも本人の「進める」を待つ
  → 下書き役 2 つが別々に「依頼書＋仮定」と「確認項目」を書く
  → 事実係が Undecided と食い違いを一覧にする
  → 話し相手が 1 画面にまとめる ─── 入口の承認（ゲート①）
  → 事実係が材料をそろえる（出典・文体カード・元データ）
  → 作り手が第 1 版（長い文書は構成案を先に ─ 確認しながらの任意ゲート）
  → 判定役が確認項目を流す（機械 AND モデル） → 不合格なら 1 行要約を作り手へ（最大 3 往復）
  → [確認しながら] 完成稿の承認（ゲート②）
     [おまかせ]   止まらず次へ
  → 届け先の形に仕立てて形式の確認項目を流す
  → [確認しながら] 送付の承認（ゲート③）
     [おまかせ]   本人だけに見える届け先なら送付し、他人に見えるなら止まる
  → 送付。案件を閉じ、決定記録を残す
```

### 3.3 本人の接点（非エンジニア向け）

本人が触るのは **libretto の画面 1 つ**。会話欄と、案件ごとの「進行」「承認」「成果」の面がある。外の面（Gmail・Slack・Drive・note）は材料の入口と成果の届け先であって、操作の場ではない。

| したいこと | 画面のどこで | 何が見えるか |
|---|---|---|
| 依頼する | 会話欄に話す | 話し相手が聞き返し、入口の 1 画面を出す |
| 候補を受け取る | 「届いた候補」の一覧 | カードごとに **由来（合図 / 推測）と確信度**、件名・誰から・頼まれていそうなこと・提案する成果物・「進める / 見送る / 内容を変える」 |
| 自動で始まったものを知る | 「自動で始まったもの」の一覧（届いた候補の隣） | おまかせの入口が自動で入れた案件。何が・いつ・どこから・今どの段階か・「取り消す」 |
| 入口で承認する | 案件の「入口」面 | 依頼書の要点・仮定・確認項目の数と種類・Undecided・モード・「これで進める」 |
| 進捗を見る | 案件の「進行」面 | いま誰が何をしているか、次に本人がすること、費用の目安 |
| 質問に答える（確認しながら） | 会話欄。質問は必ず**選択肢と推奨**付き | 例:「対象読者は A 社内の方々、または一般公開のどちらでしょう。推奨: 一般公開」 |
| 承認する（確認しながら） | 案件の「承認」面 | 完成稿、判定の結果、前の版からの変更点、「これで」「ここを直して」 |
| 成果を受け取る | 案件の「成果」面 | 版のあるページ / ドライブのリンク / ダウンロード / 貼り付け用の文章（コピーボタン） |
| 設定する | 「接続と合図」面 | 接続状態、合図（ラベル名・絵文字）、推測の範囲（見るチャンネル・メールの期間）、入口ごとの既定モード、依存の事前点検 |
| 止める | どの面にもある「止める」 | 案件 1 件の中断、または全部の緊急停止 |

**画面に出さない語**: ブランチ・コミット・PR・CI・ワークツリー・リポジトリ・デプロイ・マージ・レビュー round・モデル名・シナリオ・holdout・プロンプト。代わりに「版」「下書き」「確認項目」「検品」「承認」「送付」「やり直し」「合図」「推測」を使う。

### 3.4 画面が満たすべきこと（場面ごと）

見た目は書かない（窓口が別途デザインする）。各場面で**見せる情報**と**できる操作**だけを決める。

| 場面 | 見せる情報 | できる操作 | 満たすこと |
|---|---|---|---|
| 会話 | 本人と話し相手のやり取り。質問には選択肢と推奨 | 話す・選択肢を押す | 前提知識ゼロで読める。1 問ずつ |
| 届いた候補 | カード: **由来のしるし（「合図」/「推測」）と確信度（高 / 中 / 低）**、推測なら**拾った理由の 1 行**（「『来週までに資料を』という文があります」）、出所（メール / Slack / 会議）・件名・誰から・日時・頼まれていそうなこと 1 行・提案する成果物と届け先・「AI への指示に見える行があります（無視します）」の注意（該当時）・元へのリンク。確信度「低」はまとめて折りたたむ（「ほかに N 件、依頼かもしれないものがあります」） | 進める / 見送る（理由を 1 つ選ぶ: 依頼ではない / 自分の仕事ではない / もう済んだ / この人・この場所からは拾わなくてよい）/ 内容を変える / まとめて見送る（低の折りたたみ） | **合図由来と推測由来が一目で見分けられる**。推測は落とさず見せる（再現率優先）。見送りは理由を学習に使う（4.2） |
| 自動で始まったもの | おまかせの入口が自動で入れた案件の一覧: 何を・どこから（合図のあったメール / メッセージ）・いつ・今の段階・費用の累計 | 取り消す（下書き中なら破棄、送付済みなら「成果」から消す手順を案内）/ 開く | **本人が後から気づける**。新しく始まったものは会話欄にも 1 行出る |
| 入口 | 依頼書の要点、仮定の一覧、確認項目の数と種類と本文（折りたたみ）、Undecided の一覧、食い違い、モードと費用の上限。**自動で入ったものは「自動で入りました（合図: ラベル libretto）」のしるし** | これで進める / 直して出し直す / Undecided を決める / モードを変える / 取り消す | **1 画面で承認できる**。承認は組に 1 回 |
| 進行 | 状態、現在の版番号、検品の回数（n / 3）、直近の不合格の要約、費用の累計、次に本人がすること | 止める / 会話へ | 本人が待つ理由が分かる |
| 承認（確認しながら） | 完成稿（届け先の形で）、判定の結果（通った / 直した / 残した、出典一覧、出典なしの印、文体カードとの照合、「別系統ではありません」の表示があればそれ）、前の版との変更点 | これで / ここを直して | 判定の結果が**そのまま**載る |
| 送付の確認 | 何を・どこへ・誰に見えるか、届け先の見え方 | 送って / やめる | 他人に見える送付は必ずここを通る（おまかせでも） |
| 成果 | 届け先ごとの受け取り口。版の一覧 | リンクを開く / ダウンロード / コピー / ページの HTML をダウンロード（ほかの人に見せるときはこれを渡す。画面の文は「HTML をダウンロードして渡せます」。v1 は公開 URL を持たないので共有リンクは作らない。実装設計書 P1） | 版が切り替えられる |
| 接続と合図 | 接続の状態と権限の範囲、合図（Gmail のラベル名、Slack の絵文字）、**推測の範囲**（Gmail: 直近何日の受信箱のどのカテゴリか。Slack: 見るチャンネルの一覧と DM を含めるか）、**推測の 1 日の上限**、**推測の拾い漏れの自己測定**（本人が合図を付けたもののうち推測が先に拾えていた割合）、入口ごとの既定モード、見送りで止めた差出人・チャンネルの一覧（戻せる）、依存の事前点検、別系統と判定専用モデルの **API キーの欄**（オーナーが入れる。保存後は「設定済み」と末尾 4 文字だけ。5.7・D17） | 接続する / 外す / 合図を変える / 範囲を変える / 既定を変える / 止めた差出人を戻す / API キーを入れる・入れ直す・削除 | 権限の範囲が業務言語で分かる。保存した API キーの値は二度と画面に出ない |
| 停止 | 止めたもの・止まった理由 | 新しい入口として出し直す | 止まった案件は自動で再開しない |

### 3.5 実行基盤

常駐ホスト 1 本＋ページの形にし、モデル呼び出しは 1 か所のアダプタに閉じ込める。理由はそれぞれ下表の根拠列に書く（参考: 前者は rondo、後者は factory が先に採った形）。

| 部品 | v1 の答え | 理由・根拠 |
|---|---|---|
| ホスト | TypeScript の常駐プロセス 1 本。案件台帳と案件フォルダ（11 章）を持ち、画面を配信し、役割を起動し、**拾い上げを定期に回す**（既定 15 分ごと、画面を開いたとき、本人の求め） | 状態の正本が 1 つになり、止めて起こし直しても台帳から続きができる。拾い上げの周期も同じプロセスが持てる。参考: rondo が同じ形で動いている |
| 画面 | ホストが配信するウェブページ 1 枚。場面は 3.4。作り方は React ＋ Base UI ＋ 自前 CSS（オーナー判断 2026-10-23、実装設計書 P2・5.5） | 本人が触る場所を 1 つにし、端末や外部サービスの画面を見せない（D2）。参考: rondo のページ |
| モデル呼び出し | **アダプタ 1 か所**。入出力は「やらせる仕事・見せる材料・許可・上限・結果・費用」。中身は Claude（個人運用で `claude -p`、組織運用で Agent SDK）、**別系統（OpenAI の API を直接。Q16 = a）**、**Jev（TypeSafe の API を直接。5.7）**の 3 つ。役割ごとに別アダプタは作らない | モデルの CLI・API・鍵を知る場所が 1 か所なら、系統の差し替えと鍵の遮断（D17）が 1 か所の変更と検査で済む。参考: factory のアダプタ |
| 鍵の置き場 | **オーナーが用意し、ホストだけが持つ**。別系統の API キーと Jev のキーは**オーナーが設定の画面で入れ**、ホストが自分の機械の上の、オーナーだけが読めるファイルに置く（案件フォルダの外で、作り手のセッションから読めない場所。実装設計書 6.1・9 章）。Google の OAuth クライアントと Slack アプリの設定はホストの環境変数（`.env.local`、コミットしない）に置く。オーナー以外の使う人に登録やキーを求めない。保存したキーの値は画面に二度と出さず、各役割のセッションにも渡らない（D17） | ホストはオーナー自身の PC で動くので、キーを入れるのはオーナーになる。画面で入れられれば、ファイルを開いてキーを貼る作業を求めずに済む（人に手書きやコピペをさせない）。置き場を作り手から読めない場所に限り、画面には値を返さないので、画面・役割のセッション・リポジトリのどこにも鍵が現れない |
| 役割のセッション | 役割ごとに**新規セッション**。作り手のセッションには案件フォルダの `checks/` を読む権限を与えない（OS の sandbox で読み取り範囲を絞る。Linux / WSL2 は bubblewrap、macOS は Seatbelt で、同じ強さ。素の Windows だけは OS の仕切りが無く「隔離が弱い」と画面に出して動かす。オーナー判断 2026-10-23、実装設計書 P4・8 章） | 「読まないで」と指示しても守られたかを確かめられない。読めない場所に置けば、読めないことをテストで示せる。参考: factory lap 1 の実験で同じ結論 |
| 費用 | モデル呼び出し 1 回につき台帳に 1 行追記。**推測の分類も計上**し、1 日の上限を別に持つ | 呼び出しごとに追記すれば、上限の判定と費用の説明が台帳の集計だけで済む。推測は案件を持たないので別の上限が要る |
| Google（Gmail・Drive）の接続 | **libretto 自身が OAuth で本人の許可を取る**。Gmail: 読み取り（`gmail.readonly`。推測のために受信箱の直近分も読む）。候補にしたスレッドへ「libretto/見た」を付けるには `gmail.modify`（ラベルの付け替えに加えて、ごみ箱への移動まで含む広い権限）が要る（第 5 版まで `gmail.labels` と書いていたが、それはラベルの**定義**の作成・削除の権限で、スレッドにラベルを付けることはできない。オーナー判断 2026-10-23（実装設計書 P7 = a）: **ラベルは付けず、権限は `gmail.readonly` だけ**にする。候補になったメールは libretto の「届いた候補」に出るので、Gmail 側の印が無くても本人は分かる）。Drive: 検索・読み取り・ファイル作成。添付本体は読まない（Q9 = a。`gmail.readonly` で添付も取れてしまうので、**コードが添付を取らない**ことで守る） | 自前画面の帰結。本人のアカウントが読める範囲だけを読み、権限は最小にする（10.3） |
| Slack の接続 | libretto の Slack アプリを本人のワークスペースに入れ、**本人のユーザートークン**で動かす。権限: `reactions:read`（本人が付けたリアクションの一覧 `reactions.list`）、`channels:history` / `groups:history` / `im:history`（リアクションの付いたメッセージとスレッドの読み取り、推測のために本人が指定したチャンネルの読み取り）、`search:read`（本人宛てメンションの検索） | 4.2・Q8。`reactions.list` はユーザートークンで本人のリアクションをチャンネル・グループ・DM にわたって一覧できる（13.2） |
| Meet 議事録 | Drive の接続で「Gemini によるメモ」を検索・読み取り | 13.2 |
| 版のあるページ | ホストが案件ごとに配信（`/cases/<id>/page?v=N`）。本人だけ。共有リンクを作るのは送付（v1 は公開 URL を持たないので作らず、ページの HTML をダウンロードして渡す。実装設計書 P1） | Q11 = a |
| ファイル生成 | Node の `pptxgenjs` / `exceljs` / `docx`。描き出しと再計算は LibreOffice・poppler（Q6 = a） | 既存スキルの手順を移植 |
| 緊急停止 | ホストの外から効く（プロセスへの停止信号と、画面の「全部止める」） | 止める手段がホストの中にしか無いと、ホストが固まったときに効かない。参考: factory も外から効く停止を持つ |

**実装前に通す受け入れ確認（5 つ）**: (5) は 5.8.2（Codex あり / なしの確認項目の差を測る）。(1) 作り手のセッションから確認項目のファイルが読めないこと（canary）。(2) ホストを止めて起こし直し、台帳から「承認待ち 1 件」を言い当てて続きができること。(3) 依頼書と確認項目を別セッションが書き、確認項目の下書き役に依頼書の本文が渡っていないことを記録で示せること。(4) **推測の拾い漏れ**: 本人が過去 30 日に合図を付けた（または直接依頼した）文書づくりの依頼を集め、推測の範囲内のものを推測が候補にできた割合を測る。9 割を下回るなら前さばきと分類の文面を緩める（精度を上げる方向の調整はしない。誤検出は見送りで捌く）。

## 4. 依頼がタスクになるまで

### 4.1 直接の会話から

1. 本人の発話を受けて、話し相手が依頼の要点を聞き取る（足りない項目は選択肢付きで 1 問ずつ、推奨を添えて）。**おまかせ**を選ぶ依頼では、聞かずに**仮定**にして入口に載せる。
2. 下書き役 2 つが別々に**依頼書＋仮定**と**確認項目**を書く（5.1）。
3. 事実係が **Undecided** と**食い違い**を一覧にする。
4. 入口の 1 画面で**ゲート①**。本人は Undecided を「作り手に任せる」か「決める」かし、モードを選び、「これで進める」。承認は依頼書・仮定・確認項目・Undecided の答えの**組**に 1 回。
5. 分解の単位は「届け先に置く成果物 1 つ」で、1 成果物 = 1 作り手。

表 4-1 依頼書の項目

| 項目 | 例 |
|---|---|
| 何を作るか（4 種のどれ） | note 記事 |
| 書く内容（何について・何を入れるか） | 先週のブレストで決まった 3 つの方針と、その理由（実装設計書 6.2.3 (0) で足した。オーナー判断 2026-10-24） |
| 本人に渡してほしいもの | ブレストのメモか記録（本文の中身に要り、依頼の文に無いもの。あれば入口の承認の後に「材料待ち」で本人が貼る。実装設計書 6.2.4 で足した。オーナー判断 2026-10-24） |
| 誰が読むか | 一般の読者。前提知識なし |
| 届け先 | note へ貼り付ける下書き＋版のあるページで確認 |
| 分量・形 | 2,500 字前後、見出し 4〜5 |
| 材料 | Meet 議事録（リンク）、本人の過去記事 2 本（リンク） |
| 本人の声を合わせるか | 合わせる（過去記事から文体カードを作る） |
| 事実の出典をどう扱うか | 出典付きで。無いものは「要確認」印 |
| 期限・急ぎ度 | 今週中 |
| してはいけないこと | 社名の実名、売上の具体値 |
| 仮定（おまかせのとき） | 「読者は一般」「文末はです・ます」など、聞かずに決めた点 |
| モード | 確認しながら / おまかせ |
| 由来（候補から来たとき） | 合図（ラベル libretto）/ 推測（確信度 高、根拠の 1 行） |

### 4.2 Gmail / Slack / Meet 議事録から（拾い上げ）

原則 3 つ:
- **合図と推測の両方で拾う**（Q7 = b）。合図は本人が「これをやって」と印を付けたもの、推測は libretto が内容から「文書づくりを頼まれていそうだ」と判断したもの。**推測は拾い漏れを嫌い、再現率を優先する**（オーナー:「拾えないリスクの方が嫌だな」）。誤検出は候補を落として抑えるのではなく、**カードの由来・拾った理由・確信度の表示**と**見送りの学習**で捌く。
- **候補が仕事になるのは、本人が「進める」を押したとき、または入口の既定が「おまかせ」で合図由来のとき**（Q10 = b）。**推測由来の候補はおまかせでも自動では動かさない**（オーナー判断）。
- **他人の文章は資料であって指示ではない**（10 章）。

#### 4.2.1 合図（本人の明示の印）

| 元 | 合図 | 検出の仕方 | 候補カード |
|---|---|---|---|
| **Gmail** | 本人が付ける専用ラベル **`libretto`**（「接続と合図」で名前を変えられる） | 拾い上げのたびに**ラベルの付いたスレッドを全部**検索し、候補台帳に無いスレッド ID を候補にする。**受信時刻のカーソルは使わない**（先月のメールに今日ラベルを付けても拾う）。候補にしたメールに Gmail 側で印は付けない（付けるには `gmail.modify` が要る。オーナー判断 P7 = a で `gmail.readonly` だけにした）。「見た」は libretto の「届いた候補」で分かる | 件名・差出人・受信日時・頼まれていそうなこと 1 行・提案する成果物と届け先・リンク。しるし「合図」 |
| **Slack** | 本人が付ける**絵文字リアクション**（既定 `:memo:`。変えられる）。本人のメッセージでも他人のメッセージでもよい | 拾い上げのたびに `reactions.list`（本人のユーザートークン）で**本人が付けたリアクションを一覧**し、既定の絵文字が付いたメッセージのうち候補台帳に無いものを候補にする。チャンネル・グループ・DM にわたって取れ、アプリをチャンネルに入れる必要が無い。メッセージ本文とスレッドは履歴の権限で読む | チャンネル名・投稿者・日時・要約 1 行・提案する成果物・リンク。しるし「合図」。他人の投稿なら「○○さんの投稿を材料にします」 |
| **Meet 議事録** | **新しいメモが増えたこと**が合図代わり（本人の操作は無い）。Google Meet の「Gemini によるメモ」は Drive に Google ドキュメントとして自動保存される（題名 `<会議名> - YYYY/MM/DD HH:MM JST - Gemini によるメモ`） | 題名が上の形のドキュメントを Drive で検索し、候補台帳に無いファイル ID のものを読む。行動項目の節から**本人が担当のもの**を 1 件ずつ候補にする。節が無い・担当が読み取れないときは「行動項目を見つけられませんでした」と「行動項目なし」を区別して出す | 会議名・日時・担当アクション 1 行ずつ・提案する成果物・リンク。しるし「会議」（合図扱い。ただし「本人担当か」の読み取りには推測が混じるので確信度を付ける） |

#### 4.2.2 推測（内容から拾う）

| 元 | どこを見るか（本人が「接続と合図」で範囲を決める。既定を示す） | どう判断するか | 候補カード |
|---|---|---|---|
| **Gmail** | 受信箱の**直近 7 日**、カテゴリ「メイン」（プロモーション・フォーラム・ソーシャルは見ない）、本人宛て（To / Cc に本人）。既読・未読は問わない | 事実係が決定的に**前さばき**するのは**機械的に依頼でありえないもの**だけ（自動送信: `noreply` 等の差出人、List-Unsubscribe ヘッダ。本人が送った側のスレッド）。**依頼の語の有無では落とさない**（再現率優先）。残り全部をモデルが**分類**: 「本人に文書（記事 / メモ / 表 / スライド）を作ることを頼んでいるか」を 高 / 中 / 低 の確信度と**拾った理由の 1 行**で返す。**高・中・低をすべて候補にする**（低は折りたたみで見せる）。「頼んでいない」と判定したものだけ出さず、ID と判定を台帳に残す | しるし「推測・高 / 中 / 低」、理由の 1 行、他は合図と同じ |
| **Slack** | 本人が指定した**チャンネル**（既定: なし。本人が選ぶ）の直近 7 日と、**本人宛てメンション**（`search:read` で `@本人` を検索）。DM は既定で見ない（本人が入れられる） | 同上 | 同上 |
| **Meet 議事録** | 合図の表のとおり（新しいメモは全部読む）。本人担当と**読み取れる**行動項目は「会議」、担当が曖昧なものも「推測・低」として出す（落とさない） | 「本人担当か」の確信度を付ける | しるし「会議・高 / 中」、曖昧なものは「推測・低」 |

分類に使うモデルは Haiku を既定とし、Jev が使えるなら Jev の Noul（「この文章は、本人に文書を作ることを頼んでいる」）を併用して確信度を補う（5.7.3）。

推測の抑え方（候補を落とさずに、誤検出が本人の信頼を削らないようにする）:
- **見分けが付く表示**: 合図由来と推測由来はしるしが違い、推測は確信度と拾った理由の 1 行を必ず伴う。カードの並びは合図 → 会議 → 推測・高 → 推測・中 → 推測・低（折りたたみ）。
- **見送りの学習**: 見送りの理由が「この人・この場所からは拾わなくてよい」なら、その差出人（メールアドレス）またはチャンネルを**推測の対象から外す**（合図は外さない）。「依頼ではない」が同じ差出人・チャンネルで 3 回続いたら「外しますか」と本人に 1 回聞く（勝手には外さない）。外したものは「接続と合図」の面で見られ、戻せる。「もう済んだ」「自分の仕事ではない」は学習に使わない。
- **閾値は設けない**: 候補を確信度で落とさない。本人が「低は要らない」と言ったときだけ「接続と合図」で低の表示を消せる（既定は表示）。受け入れ確認 (4) は再現率を測る。
- **費用と頻度の上限**: 分類は 1 日の上限（既定 300 通・件）を持ち、超えたら翌日に回し、「接続と合図」に「今日は N 件を見られませんでした」と出す（黙って落とさない）。
- **重複**: 合図と推測で同じスレッド・メッセージが拾われたら、候補は 1 件で**由来は「合図」**にする。
- **自己測定**: 本人が合図を付けた候補について「推測が先に拾えていたか」を台帳で数え、「接続と合図」に割合を出す。拾えていなかったものは分類の文面を直す材料にする（本人の確認なしに読み直すのは件名・差出人まで。本文は読み直さない）。

#### 4.2.3 候補が仕事になるまで

| 入口の既定モード | 合図由来の候補 | 推測由来の候補 |
|---|---|---|
| 確認しながら | カードで本人が「進める」→ 4.1 の手順 2 へ | 同じ |
| おまかせ | **自動で入口へ**（Q10 = b）。下書き役が依頼書と確認項目を書き、Undecided は「作り手に任せる」として**入口の承認を省いて**下書きへ進む。「自動で始まったもの」に記録し、会話欄に 1 行。入口の画面は出す（見られる・取り消せる）。D5 の線で止まる | **自動では動かさない**（オーナー判断）。カードで本人が「進める」→ 以降は合図由来と同じ扱い |

例外: 「AI への指示に見える行」の印が付いた候補は、合図由来でも自動では入れない（10.1）。

「進める」の後（または自動で入った後）は 4.1 の手順 2 に入る。候補カードの「頼まれていそうなこと」は依頼書の下書きであって依頼書ではない。

**候補の記録と重複の除き方**:
- 候補 1 件ごとに**安定した ID**（Gmail: スレッド ID。Slack: チャンネル ID ＋メッセージ ts。Meet: ファイル ID ＋行動項目の文の指紋）。
- 候補は**カードを出す前に**データベースの候補の台帳（11 章）へ書く（由来・確信度・根拠を含む）。出し終えたら「提示済み」。
- **見送った候補は再提案しない**（同じ ID を飛ばす）。同じメモの他の項目や後から増えた項目は新しい ID。
- 合図の検索対象は**毎回全部見直す**ので時刻カーソルを持たない。推測の走査窓（直近 7 日）は窓であってカーソルではない（窓の中は毎回見直し、台帳で重複を除く。「頼んでいない」と判定したものは再分類しない）。

**添付ファイルについて**: v1 は添付本体を読まない（Q9 = a）。添付が材料になる候補ではカードに「添付『見積書.xlsx』が材料に要ります。画面に貼るか、ドライブに置いてください」と出し、届くまで「材料待ち」で止める（おまかせでも）。

### 4.3 聞き返しの作法（確認しながら）

- 1 回の問いに選択肢は 2〜4 個、推奨 1 つ、推奨の理由 1 行。
- 本人の答えを待つ間、答えに依存しない準備は進めてよい。答えに依存する下書きは始めない。
- 期限や沈黙で答えを決めない。

### 4.4 おまかせでの扱い

- 聞きたいことは**仮定**として依頼書に書き、入口で本人が仮定ごと承認する。入口のあとは人に聞かない。
- 作り手の途中の疑問も仮定にして下書きに注記し、判定役が印として扱う。
- 止まる場面（D5）に当たったら、その案件は「送付確認待ち」か「停止」で止まり、本人に 1 行通知する。返事は待たない（他の案件は進む）。
- **自動で入った案件**は「自動で始まったもの」に残り、どの段階でも取り消せる。取り消しは下書き中なら破棄（費用は台帳に残る）、送付済み（本人だけに見える届け先）なら「成果」の面から消す手順を案内する。

### 4.5 話し相手の文面の点検

話し相手が本人に出す文は、出す前に次を自分で確かめる:
- 前提知識ゼロで読めるか
- 直訳調マーカーが無いか
- 選択肢と推奨があるか（質問のとき）

## 5. 文書の検品（物差しを作り手に見せない方式）

### 5.1 入口で 2 つを別々に下書きする

| 下書き | 誰が | 渡すもの | 渡さないもの | 出すもの |
|---|---|---|---|---|
| **依頼書** | 下書き役（依頼書） | 依頼・材料・本人の過去文書 | 確認項目 | 表 4-1 と仮定の一覧 |
| **確認項目** | 下書き役（確認項目）。**別セッション、Codex（別系統）**（Q3 = a）。Codex が無い環境では Claude の別セッション（5.8） | 依頼・材料・依頼書の**形だけ**（文書の種類・届け先・分量・見出し数） | 依頼書の本文・仮定 | 確認項目の一覧（5.2 の型。合格条件は**肯定形の命題**）。各項目に「依頼に書いてある / 書いていない」の自己申告と、不合格のときの 1 行要約 |

依頼書の「形だけ」を渡す理由: 確認項目が文書の種類・届け先・分量と食い違わないために最低限要る情報であり、依頼の中身の解釈は渡さない。仮定を渡さない理由: 仮定は依頼書側が「決めていないこと」に置いた答えで、確認項目側に渡すと同じ答えを前提にした項目だけになり、別々に書く意味が消える（参考: factory lap 2 で同じことが起き、渡さない形に直した）。

事実係が **Undecided と食い違い**を一覧にする: 確認項目の各項目について、依頼書だけを見た別セッションが「依頼書からこの項目の答えが決まるか」を予測し、確認項目の期待と機械的に照合する（factory の「独立した分類」）。入口の画面に載せ、本人が「作り手に任せる」か「決める」かを選ぶ。libretto は自動で直さない。

### 5.2 何が確認項目になるか

確認項目は「**何を・どう確かめ・何なら合格か**」の 3 つ組で書く。合否は **機械判定 AND モデル判定**。

| 種類 | 観点 | 確認項目の例 | 判定の材料 |
|---|---|---|---|
| **機械判定**（決定的コード） | 分量 | 「本文は 2,200〜2,800 字」 | 文字数 |
| | 構成 | 「見出しは 4〜5 個、各見出しの下に 2 段落以上」 | 見出し解析 |
| | 禁止事項 | 「社名 X・Y が本文に無い」「金額の具体値が無い」 | 文字列・正規表現 |
| | 出典の到達 | 「出典付きの主張は全部、出典が開けて該当箇所が切り出せる」 | 事実係の取り寄せ（5.4） |
| | 数値の転記 | 「材料の数値 12 個が最終版で同じ値」 | 事実係の照合 |
| | 文体の数値 | 「文末の『です・ます』率 90% 以上、一文の中央値 45 字以下、一人称は『私』のみ」 | 文体カードとの距離 |
| | 形式 | 「貼り付け用に表・脚注記号・HTML が無い」「xlsx に式エラーが無い」「pptx の描き出しに空白ページが無い」 | 7 章の形式検査 |
| | 棚卸しの網羅 | 「事実の主張は全部、出典あり / 材料由来 / 要確認印 のどれかに分類されている」 | 5.4 |
| **モデル判定**（判定役のセッション） | 事実の支持 | 「主張 n は出典 m のこの箇所に支持されるか」 | 事実係の表と抜粋 |
| | 依頼適合 | 「初見で読んだ人が『ブレストで何が決まったか』を 3 行で言えるか」 | 完成稿 |
| | 文体の読み比べ | 「本人の過去記事の段落と並べて、別人が書いたと分かるか」 | 文体カード・過去記事の抜粋 |
| | 日本語の自然さ | 「直訳調マーカーが残っていないか」「造語・社内用語に初出の説明があるか」 | 完成稿 |
| | 見た目 | 「スライド 3 枚目の図は枠に収まり、文字が重なっていないか」 | 描き出した画像 |

**作り手に見せないことに意味がある項目**と**見せても同じ項目**:

| 見せない意味がある（確認項目に入れ、作り手に渡さない） | 見せても同じ（依頼書に書き、確認項目にも入れる） |
|---|---|
| **読者の問い**。見せると作り手がその問いの答えだけを書く | 分量・見出し数・禁止事項・届け先の形 |
| **事実照合の対象の選び方**。見せるとそこだけ丁寧になる | 出典を付けること自体 |
| **文体の読み比べに使う本人の段落**。見せると模倣になる | 文体カードの数値 |
| **少数派の確認**（本人の癖のうち作り手が見落としやすい点） | — |
| **形式の落とし穴**。見せると「確認項目に無い落とし穴」を見なくなる | — |

### 5.3 判定と、不合格のときに返すもの

- 判定役は**作り手と別セッション**で、依頼書・確認項目・下書き・事実係の表だけを読む。
- 機械判定を先に流し、全部通ったらモデル判定。**どちらかが落ちれば不合格**（AND）。
- 不合格のとき作り手に返すのは、**落ちた確認項目の 1 行要約だけ**。要約は入口で承認した確認項目に**あらかじめ付けておく**。
- 往復は**最大 3 回**（Q2 = a）。3 回で消えない項目は、確認しながらでは本人に上げ、おまかせでは**失敗として止める**。
- **3 回目を待たずに上げる**（GitHub #48。オーナー決定 2026-10-24: 案 b）: 同じ項目が 2 回続けて機械判定で落ち、合格までの距離が縮んでいないとき、または作り手に返せる要約が 1 つも無いとき（落ちたのが判定できなかった項目だけ）は、往復が残っていても本人に上げる（おまかせでは止める）。直らない往復に費用を使わないため。測り方は実装設計書 6.2.7。
- **判定できなかった項目は作り手に返さない**（GitHub #48）: 判定役が決められなかった項目は、作り手が直せる指摘ではない（何が足りなくて決められなかったかは作り手から見えない）。要約は本人にだけ見せる。
- 判定の結果は `review-NN.md` に残り、承認の画面にそのまま載る（モデル判定の理由文は `review-NN.reasons.md`。本人は見られ、作り手は見られない）。

### 5.4 事実係の取り寄せと棚卸し（決定的コード）

- **棚卸しは完成しようとしている版の全文に対して行う**。事実の主張＝数値・日付・固有名詞・比較や断定・表計算のセルの値。Haiku が候補を抜き出し、コードが位置を付ける。
- 各主張を 3 つに分ける: **出典あり** / **材料由来**（元の値と突き合わせる）/ **出典なし**（「要確認」印が付いていれば通し、無ければ**不合格として作り手に戻す**。Q4 = a）。本人には承認の面で印の付いた形で見せ、「印のまま出す」か「削る」かを選べる。
- 出典が URL なら本文を取得して該当段落を切り出す。Drive なら読み取り接続で開く。添付は本人が渡したものを読む。開けない・該当箇所が見つからないときは「開けない」と記録し、不合格になる。
- `facts.md` には「主張 / 位置 / 出典の場所 / 出典本文の指紋 / 判定」。**引用抜粋は案件が開いている間だけ** `facts-excerpts/`。
- **数値の照合**は最終版に対してもう一度行う。
- 数値・日付・固有名詞の転記は、材料から**コードが抜き出して**作り手に渡す。

### 5.5 文体カード（本人の声）

本人が書いた文章から**決定的に**抽出し、`voice.md` に置く。

| 項目 | 抽出方法 |
|---|---|
| 文末形の分布 | 「です・ます / だ・である / 体言止め / 〜と思う・〜かもしれない」の割合 |
| 一文の長さ | 中央値と上限（字数） |
| 一人称・読者の呼び方 | 「私 / 僕 / 筆者 / なし」「あなた / 読者 / みなさん」 |
| 句読点・記号 | 読点の頻度、「！」「？」「（）」「—」の使用、英数字の全半角 |
| 漢字率・カタカナ語の頻度 | 字種の割合 |
| よく使う言い回し・避けている言い回し | 頻出の接続語・文頭語の上位、使っていない定型句 |
| 段落の長さ・見出しの付け方 | 段落あたりの文数、見出しの体言 / 文 |

末尾にモデルが書く **3 行の人物描写**を付ける。**読み比べに使う本人の段落**は確認項目側に置き、作り手には渡さない。

### 5.6 検品の方式を選んだ理由（参考にした実験結果）

各判断の理由は右列で完結するように書く。左列は参考にした factory の実験結果（`factory-notes/laps/`）で、判断の根拠ではなく「同じことが別の場でも起きた」という裏付けである。

| 参考にした実験結果（factory） | libretto での判断と理由 |
|---|---|
| 不合格の 1 行要約を返すと、作り手は要約が述べた点だけを直し、後退 0 件で 2 回目に収束した（lap 6） | 不合格は**要約を返す**。理由: 理由文を渡すと作り手は確認項目の中身を逆算でき、隠す意味が消える。1 行要約でも作り手は直す点を特定できる。要約を入口で承認したものに固定するのは、漏れが無いことを本人が入口で確かめられるようにするため |
| 下書き役の「少数派」の見立てが外れ、入口の確認で見つけて外した。期待値の誤りは工場の外で見つけた（lap 5・6） | **物差し自体の不具合**は作り手の不出来に見える（確認項目が間違っていると正しい下書きが落ち続ける）。だから入口で Undecided と食い違いを一覧にし、本人の過去文書があるときは**確認項目を本人の過去文書に流して**「本人の文章が落ちる項目」を入口で見せる |
| LLM 判定は全試行を承認し、合否は決定的テストだけで決まった（lap 6） | 機械判定 AND モデル判定。理由: モデル判定は甘くなりがちで、機械判定が合否を決める形にしないと物差しが効かない。モデル判定だけで決めない |
| 同系統のモデルは作る役と下書き役で同じ答えを選ぶ（lap 5） | 確認項目の下書きに**別系統**を使う（Q3）。理由: 同じ系統は同じ思い込みを共有し、物差しが作り手を試さない |
| 隠すには sandbox が要る（lap 1） | 作り手の読み取り範囲を OS の sandbox で絞る。理由: 指示で隠しても守られたかを確かめられない。受け入れ確認 (1) で読めないことを示す |
| 仮定の文を渡すと隠す意味が消えた（lap 2） | 確認項目の下書き役に依頼書の本文と仮定を渡さない。理由: 渡すと同じ答えを前提にした項目だけになる（5.1） |
| 試行上限は 3 → 5 回（lap 3）。費用は 1 変更 $0.5〜14 | 文書は 1 往復で直ることが多いので 3 回（Q2 = a）。3 回で消えない項目は物差しか依頼書の問題で、本人判断に向く。費用上限は案件ごと ¥1,500 相当（Q13 = a。1 変更の実測が $0.5〜14 だったことから 1 案件 $10 前後を見込んだ） |

### 5.7 判定役に Jev（判定専用モデル）を使う案

オーナーの発案（「判定に Jev を使うのがいいかもね」）。Jev は TypeSafe AI の判定専用モデルで、文章を書かず、渡した材料（state）について「どれか（Choice）」「はい / いいえ（Noul、0〜1 の確率）」「何段階か（Score）」を**確率と自信度（confidence）付きで**返す。オーナーは既に 2 つのプロダクトで使っている（`jev-party` 大喜利の審査員、`jev-soup` ウミガメのスープの出題者）。以下は両リポジトリのコードと測定記録から確かめた（13.1・13.2）。

#### 5.7.2 文書の確認項目のどれに向くか

Jev は「材料を渡して、短い命題に確率で答える」役で、**テキストしか読めない（画像は受け取れない）**。5.2 のモデル判定を、Jev に出せる形（**1 項目 1 Noul、state は短い抜粋、肯定形の命題、テキスト**）に直せるかで分ける。**画像を見る判定（スライド・Word の描き出し画像のはみ出し・重なり・空白ページ、Google スライドへ変換した後のスクリーンショット照合）はすべて Claude（視覚）に残す**（オーナー）。

| 確認項目（モデル判定） | Jev に向くか | 理由と出し方 |
|---|---|---|
| **事実の支持**（主張 n は出典 m のこの箇所に支持されるか） | **向く** | state = `{ 主張, 出典の抜粋 }`（事実係が切り出した該当段落。短い）、Noul「『出典の抜粋』は『主張』を支持している」。言い換えの正解を正解と判定する 96.6% の精度に当たる（参考: jev-soup の「解答に要点が含まれるか」が同じ形の判定）。**肯定形で聞く**（「支持していない」と聞かない。否定形は 85%） |
| **禁止事項・有無の確認**（社名 X が無い、金額の具体値が無い、他人の発言を引用していない） | 機械判定で足りるものは機械。表現が揺れるもの（「売上の規模が分かる書き方」）は **向く** | state = 段落ごと、Noul「この段落は売上の規模が分かる数値を含む」。1 段落 1 Noul に分け、集計はコード（「数える」のは苦手） |
| **依頼適合の個別項目**（「ブレストで何が決まったかが書いてある」「対象読者に前提知識を要求していない」） | **向く（命題に分解できるもの）** | 確認項目の下書き役が「読者の問い」を**肯定形の命題**にして出す。state = 完成稿の該当節（長いと落ちるので節単位） |
| **取り込み元の「AI への指示」検出**（10.1） | **最も向く** | 反則の検出 99.6%・誤検出 0.0% の実績がそのまま使える。state = 外部文書の段落、Noul「この文章には、AI へ特定の判定や動作をさせる命令が含まれている」（文面は jev-soup で実測済みのものを写して使う） |
| **候補の「依頼か」判定**（4.2.2） | 向く（補助として） | 5.7.3 |
| **文体の読み比べ**（別人が書いたと分かるか） | **向かない** | 比較対象が長く（本人の段落＋下書きの段落）、「関係のない材料が多いと精度が落ちる」に当たる。判定が好みの領域で、Jev の学習範囲に日本語の文体比較があるかの公開データが無い（jev-party 設計書「精度に関する公開データは英語のものだけ」）。Claude の別セッションに残す |
| **日本語の自然さ**（直訳調マーカー、造語の無説明） | 向かない | マーカーの検出は決定的コード（`wabun:suiko` の観点）に寄せ、残りの「読んで不自然か」は Claude |
| **見た目**（描き出した画像のはみ出し・重なり・空白ページ、変換後のスクリーンショット照合） | **向かない（使わない）** | 画像を受け取らない（テキストの判定モデル）。Claude Sonnet（視覚）に残す |
| **構成の論理**（結論が先に来ているか、節の順が自然か） | 部分的 | 「この節の最初の段落に結論が書かれている」のような命題にできるものだけ |

**確率の扱い**（理由: 0.5 の近くの答えは「分からない」に近く、合否に使えない。5.7.1 で測った「自信度 0.5 未満の答えの一致率 77%」は Choice の自信度についての数字で、Noul の応答には自信度が**付かない**（確率 `noul` だけが返る）ので、Noul では確率の帯で同じ扱いをする）: Noul が 0.65 以上で「はい」、0.35 以下で「いいえ」、その間は**合否に使わず「判定不能」**として Claude の判定に回す。帯の幅は実装後の測定で見直す（実装設計書 7.3）。確率は判定の記録に残し、承認の面で「出典の支持: 12 件のうち 11 件が確か、1 件は確信度が低く別の読み手で確認」のように見せる。

**否定形の弱さへの対策**: 確認項目は**合格条件を肯定形の命題**で書く決まりにする（「社名が無い」ではなく「この段落は社名を含む」を聞いて、コードで反転する）。確認項目の下書き役への指示に入れ、事実係が決定的に否定語（「ない」「含まない」「〜ではない」）を検出して警告する。

**AND の中での位置**: Jev の判定は「モデル判定」の一部で、機械判定の後に流す。Jev と Claude の両方に出した項目は**どちらかが落ちれば不合格**（AND を保つ）。Jev だけに出した項目で「判定不能」が出たら Claude に回す（落とさない）。

#### 5.7.3 推測の「依頼か」判定に Jev を使うか

向く。Noul「この文章は、宛先の人に文書（記事・メモ・表・スライド）を作ることを頼んでいる」を、メール・メッセージの本文を state に置いて聞く形は肯定形の命題なので、5.7.1 の実測から 99% 級の精度が見込める（参考: jev-soup の「質問に答える」と同じ構造）。ただし:
- **再現率優先**（D3）なので、Jev の Noul は**確信度の材料**に使い、候補を落とすのには使わない。Haiku の分類（理由の 1 行を書ける）と Jev の確率を並べて、高 / 中 / 低を決める（Jev 0.7 以上かつ Haiku 高 → 高、どちらか → 中、Jev 0.3 以上または Haiku 低 → 低、両方「頼んでいない」→ 出さない）。
- 本文が長いメールは精度が落ちる（「関係のない材料が多い」）。state は本文の先頭 600 字＋件名に絞る。
- 費用は 1 件あたり 1,000 トークン前後で、1 日 300 件でも 1 円に満たない。遅延は数秒で、拾い上げは 15 分ごとなので問題にならない。
- Jev が使えないときは Haiku だけで分類する（確信度は Haiku のみ）。

#### 5.7.4 費用・遅延・キー・使えないとき

| 観点 | libretto での扱い |
|---|---|
| 費用 | 1 案件の確認項目 20〜40 件 × 1 Noul（state は抜粋）で 2〜4 万トークン、$0.001〜0.002。推測の分類を含めても月 10 円に届かない。費用台帳（データベースの費用の表。11 章）に Jev も 1 呼び出し 1 行で載せる |
| 遅延 | 1 リクエスト数秒。確認項目は 1 案件分を**数リクエストにまとめて**並列に送る（1 リクエストに複数の質問を並べられる。5.7.1）。10 秒でタイムアウト、429 / 529 は 2 回まで再試行（遅延が数秒なので 10 秒で十分、再試行 2 回で一時的な混雑を越えられる。参考: jev-soup と同じ値） |
| キー | Jev のキーを**オーナーが用意して設定の画面で入れ**、**ホストだけが持つ**（オーナーだけが読めるファイル。保存後の画面には「設定済み」と末尾 4 文字だけを出す）。オーナー以外の使う人に登録やキーを求めない（別系統の API キーと同じ扱い。D17）。作り手・下書き役・判定役のセッションには渡さない。モデル呼び出しのアダプタの 1 つの中身として扱い、役割側は「判定を頼む」だけ |
| 1 日の上限 | 費用台帳の集計で数え、上限で「今日は Jev を使えません」と「接続と合図」に出す。上限後は Claude に回す |
| 使えないとき | (1) ホストにキーが入っていない: Jev の項目をすべて Claude の別セッションで判定し、承認の面に「判定専用モデルは使っていません」と表示。(2) 一時的なエラー・タイムアウト: その項目だけ Claude に回す。(3) 「判定不能」（Noul の確率が 0.35〜0.65 の帯）: Claude に回す。いずれも**落とさない・黙らない** |
| 入手の道 | オーナーが既に持つキーを使う。TypeSafe の直接登録が止まっている間に新しいキーが要るなら Vercel AI Gateway / OpenRouter 経由（jev-party 設計書）。アダプタの中身の差なので役割側は変わらない |

#### 5.7.5 三系統の分担（Q3 = a、決定）

系統は Claude（話し相手・下書き役（依頼書）・作り手・文体 / 自然さ / 構成 / 画像の判定）、Codex（確認項目の下書き）、Jev（テキストで命題にできる判定）の 3 つ。factory lap 5 の「同系統は答えが揃う」に対して、物差しを作る側（Codex）と測る側（Jev）の両方を作り手（Claude）と別にできる。Codex が無い環境は 5.8。

### 5.8 Codex が無い環境での確認項目の下書き

オーナーのコメント「codex がない場合を考慮して」への答え。別系統は**ホストが OpenAI の API キーで直接呼ぶ**（Q16 = a。キーはオーナーが用意しホストだけが持つ。D17）ので、使う人に Codex CLI のログインを求める場面は無い。それでも**キーが入っていない環境**（オーナーが設定の画面でキーを入れていない、キーの失効、API の障害）はありうるので、無い環境を既定の 1 つとして設計する。以下「Codex が無い」は「別系統のキーがホストに無い、または呼べない」を指す。

#### 5.8.1 どうするか

| 段 | Codex がある | Codex が無い |
|---|---|---|
| 確認項目の下書き | 別系統（OpenAI の API）の新規セッション。依頼・材料・依頼書の形だけを渡す | **Claude の新規セッション**。渡すものは同じ（依頼書の本文と仮定は渡さない。別セッションの分離は保つ）。加えて指示に **「少数派を選ぶ」**を入れる: 依頼が決めていない点について、作り手が選びそうな答えではなく**筋の通る別の答え**を 3 件以上、確認項目にする（factory lap 6 の minority choice。入口で本人が見て外せる） |
| 確認項目の点検（入口の前） | 事実係の「独立した分類」（Claude の別セッション） | **Jev で点検する**（第三系統が使える範囲で使う）: 各項目について Noul「この項目の合格条件は、依頼文から導ける」（state = 依頼文・項目）→ 0.5 未満を Undecided の候補に。Noul「この項目の合格条件は肯定形の命題で書かれている」→ 0.5 未満は書き直しを 1 回だけ下書き役に戻す。Noul「この項目は、文書の種類・分量・届け先の形についてだけ述べている」が高い項目は**作り手に見せても同じ項目**（5.2 右列）として入口に区別して出す |
| 本人の過去文書での点検 | 5.6 のとおり（本人の文章が落ちる項目を入口で見せる） | 同じ。同系統の下書きでは本人の癖と違う物差しが増えやすいので、**この点検を必須にする**（過去文書があるとき） |
| 入口の表示 | 「確認項目: n 件（別系統）」 | **「確認項目は、作り手と同じ系統の AI が書きました。見落としが重なることがあります」**を入口の面の確認項目の見出しに常に出す。少数派の項目には「別の答えを選ぶ確認」のしるし |
| 承認の面の表示 | 判定の結果 | 同じ注意書きを判定の結果の冒頭にも出す |
| 判定 | Jev（命題）＋ Claude（残り） | 同じ（Codex の有無は判定に関係しない） |

#### 5.8.2 品質はどう落ちるか（根拠）

- 同系統の 2 セッションは学習が同じなので、依頼が決めていない点で**同じ答えを選び、散らばらない**。確認項目が作り手の思い込みと同じものを測るだけになりやすい。参考: factory lap 5 で同じことが観察され、lap 1 では 15 本のうち 14 本が「仕様に書いてある振る舞い」で、隠しても作り手を試していなかった。
- 期待できる落ち方: 「依頼に書いていない」側の項目（読者の問い・少数派の確認・形式の落とし穴）が減り、作り手が見落とす点を確認項目も見落とす。「依頼に書いてある」側（分量・禁止事項・出典の到達）は機械判定なので系統に関係なく効く。**事実の支持と「AI への指示」検出は Jev が判定する**ので、Codex の有無で落ちない。
- 落ちを埋める手当て: 少数派を選ばせる指示（依頼が決めていない点で作り手が選びそうでない答えを項目にすれば、作り手を試す項目になる。参考: factory lap 6 で作る役が 1 回目に落ちた項目は少数派の 2 本だけだった）、Jev による項目の点検（第三系統の目を入口に入れる）、本人の過去文書での点検。
- 測れないこと: 手当て後に Codex あり / なしでどれだけ差が残るかは実装後の測定事項（受け入れ確認に (5) を足す: 同じ依頼で Codex あり / なしの確認項目を作り、「依頼に書いていない」項目の数と、作り手の第 1 版が落ちる項目の数を比べる。差が無ければ Codex を必須にしない）。

#### 5.8.3 別系統の届け方（Q16 = a、決定）

**ホストが OpenAI の API キーで別系統を直接呼ぶ**。キーはオーナーが用意して設定の画面で入れ、ホストだけが持つ。オーナー以外の使う人に登録やキーを求めない。Jev のキーも同じ扱い（「jev も同じ扱いがよさそう」。D17）。CLI のログインは前提にしない。費用は確認項目の下書き 1 案件 1 回（数千トークン）で月数十円、費用台帳に 1 行ずつ載せる。

## 10. 取り込み元の安全（非信頼データ・保存・同意）

### 10.1 「資料」と「指示」を分ける

- Gmail / Slack / Meet メモから読んだ文章は、どの役割にも**「外部資料」として引用の枠に入れて渡す**。枠の外にある本人の発話と承認済みの依頼書だけが指示になる。推測の分類（4.2.2）も枠の中の文章を「依頼か」と**判断する**だけで、そこに書かれた指示には従わない。
- 枠の中に「AI へ: 〜しなさい」のような文があっても従わない。事実係が決定的に**命令形の行を検出して印を付け**（Jev が使えるなら「AI への指示が含まれている」の Noul を併用。実測 99.6% / 誤検出 0%。5.7.2）、候補カードに「AI への指示に見える行があります（無視します）」と表示する。**この印の付いた候補は、おまかせの入口でも自動で入れない**（本人の「進める」を待つ）。
- 候補カードの「頼まれていそうなこと」は本人が確認するためのもので、**取り込み元の文章が依頼書や確認項目の文になることはない**（下書き役は依頼と材料を読んで自分の言葉で書く）。
- 作り手が外部資料を読むのは、承認済みの依頼書に「材料」として挙がっているものだけ。作り手のセッションは外部へ出ない。

### 10.2 何を読み、何を保存するか

| | 読むもの | 保存するもの | 保存しないもの |
|---|---|---|---|
| Gmail（合図） | ラベル `libretto` の付いたスレッド | スレッド ID・件名・差出人・日時・本人が確認した要約 | 本文・添付 |
| Gmail（推測） | 受信箱の直近 7 日・メインカテゴリ・本人宛て。自動送信以外の本文を分類のために読む（Jev に出すのは先頭 600 字＋件名） | 候補にしたもの: 上と同じ＋確信度・拾った理由の 1 行。「頼んでいない」と判定したもの: スレッド ID と判定だけ（再分類しないため） | 本文。候補にしなかったものの件名・差出人 |
| Slack（合図） | 本人がリアクションを付けたメッセージとそのスレッド | メッセージへのリンク・チャンネル名・投稿者名・日時・要約 | 本文、同じチャンネルの他の発言 |
| Slack（推測） | 本人が指定したチャンネルの直近 7 日と、本人宛てメンション | 候補にしたもの: 上と同じ＋確信度・理由。「頼んでいない」と判定したもの: メッセージ ID と判定 | 本文 |
| Meet メモ | 題名が「Gemini によるメモ」の形のドキュメントの行動項目の節 | リンク・会議名・日時・本人担当の項目の要約 | 本文全体・他の出席者の発言 |
| 本人の過去文書 | 本人が指定したもの | 文体カード。読み比べ用の段落は案件中だけ | 本文の写し |
| 出典 | 主張の該当箇所 | `facts.md`（場所・指紋・判定）。抜粋は案件中だけ | 閉じた後の抜粋 |

推測のために読んだ他人のメール・メッセージは、**候補にしなかったものについて本文も件名も残さない**（ID と判定だけ）。候補にしたものも、本人が見送れば要約を消して ID と「見送り（理由）」だけにする。Jev に送った本文は TypeSafe 側に渡る（保存の有無は契約次第。jev-party 設計書は Gateway 経由で「送った内容を保存しない設定」を選べると書く）。推測に Jev を使うかは「接続と合図」で本人が切れる（既定: 使える環境なら使う）。

### 10.3 同意と見える範囲

- 読めるのは**本人のアカウントが読める範囲**だけ。OAuth の権限は 3.5 の表のとおり最小にし、「接続と合図」の面に業務言語で出す（「メールを読みます（送りません・ラベルも付けません）」「Slack であなたが絵文字を付けたメッセージと、選んだチャンネルを読みます」）。
- **推測の範囲は本人が決める**（既定: Gmail は直近 7 日のメイン、Slack はチャンネル指定なし＋メンション）。他人の DM を推測の対象にするのは本人が明示的に入れたときだけ。
- 他人の発言を**成果物に引用する**ときは、依頼書の「材料」に挙がっていて、かつ本人が承認した場合に限る（おまかせでも引用のある成果物は送付前に止まる）。
- 成果物を Drive に作るとき、**共有は libretto からはしない**。
- 他人の投稿にリアクションして拾う場合、その人の文は「材料」であり、依頼主は本人である。候補カードに「○○さんの投稿を材料にします。本人に断りますか」の 1 行を添える。

## 11. 状態と再開

### 11.1 置き場

```
libretto/
  libretto.db              データベース（SQLite 1 ファイル）。状態と台帳を全部ここに持つ（作り手のセッションから読めない場所）
                             案件: id・題・状態・モード・由来（会話 / 合図 / 推測）・自動で入ったか・届け先・作成日・最後の更新
                             案件の出来事: 遷移 1 回 1 行（追記専用）
                             候補: 候補 id・出所・由来（合図 / 推測 / 会議）・確信度・根拠の 1 行・提示済みか・進める / 見送り（理由）/ 自動で入口へ・結び付いた案件 id
                             候補カードの中身: 件名・差出人・要約（見送りで消せる行）
                             推測から外した差出人・チャンネル（理由・日時。戻せる）
                             費用: モデル呼び出し 1 回 1 行（案件 id または「推測」・役割・モデル・費用・日時）
                             承認の記録: ゲート・日時・版番号・本文の指紋・届け先・組の指紋・「自動（おまかせ）」か本人か
                             送付の記録: 届け先・版番号・状態・受領 id・日時・誰に見えるか
                             本人の答えと日時
  cases/<案件 id>/         文書の置き場（ファイル）
    brief.md               依頼書と仮定（入口で承認した版）
    checks/                確認項目（作り手のセッションから読めない場所）
      checks.md              項目・判定の仕方・合格の条件・不合格のときの 1 行要約
      voice-samples.md       読み比べ用の本人の段落（閉じるときに消す）
    undecided.md           Undecided と食い違いの一覧と、本人の答え
    voice.md               文体カード
    facts.md               主張 / 位置 / 出典の場所 / 指紋 / 判定
    facts-excerpts/        出典の引用抜粋（閉じるときに消す）
    outline.md             構成案（任意）
    draft-01.md draft-02.md …   版
    draft-01.done …        版の完了印（本文の指紋）
    review-01.md …         判定の結果
    review-01.reasons.md … モデル判定の理由文
    decisions.md           本人の答えと日時（データベースから描き出す読む用）
    intake.md              拾い上げの出所（リンク・ID・要約・由来・確信度）
```

状態はデータベースの案件の行の `state` 1 列（遷移の出来事と同じトランザクションで書き換える）: `候補 / 入口待ち / 材料待ち / 下書き中 / 検品中 / 承認待ち / 送付確認待ち / 送付中 / 完了 / 停止 / 見送り / 取り消し`。

書き方の約束:
- **書き込みは 1 遷移 1 トランザクション**。1 回の遷移で書くもの（状態・出来事・承認・送付・費用）は、全部書けるか全部書けないかのどちらかになる。
- **出来事は追記専用**。遷移・承認・送付・費用の行は書き換えず消さない（取り消しも「取り消した」行を足す）。後で消すもの（他人の要約・出典の抜粋・読み比べの段落）は追記専用の表に入れず、消せる行かファイルに置く。
- **版は書き終えてから完了印を付ける**。
- **承認は組に結び付ける**。おまかせで自動に進んだ承認は承認の記録に「自動」と残し、入口の面に表示する。
- **送付は 3 状態**（送付中 / 送付済 / 不明）。「不明」は再送せず届け先側で受領 id を探す。
- **費用は呼び出しごとに追記**し、案件ごと（¥1,500 相当）・全体・推測の 1 日上限と比べる。上限に達したら「停止」（推測は翌日に回す）。

### 11.2 再開

- ホストを止めて起こし直しても、データベースとフォルダで全部が分かる。起動時に「承認待ちが 1 件、自動で始まったものが 2 件あります」と進行の面に出す。
- 作り手は完了印の付いた最後の番号から続く。往復の上限は `review-NN.md` の数で数える。
- 拾い上げは時刻カーソルを持たない。未提示の候補は次回そのまま出る。推測の走査窓は窓であってカーソルではない。
- 「停止」「取り消し」の案件は自動で再開しない。

### 11.3 git を使わない理由

版の履歴は番号付きファイルで足り、「変更点」は 2 版の差分を本文の単位で出せばよい。ブランチ・マージ・PR は文書の作業に対応物が無く、画面に出せない語でもある。

### 11.4 状態と台帳に SQLite を使う理由

オーナー判断（2026-10-23）。状態と台帳は SQLite のデータベース 1 つに置き、文書（版・確認項目・判定・文体カード・出典の抜粋・ページの HTML）はファイルのまま案件フォルダに置く。理由は 3 つ。

1. **書き込みの順序をトランザクションが与える。** 状態の遷移には、承認・送付・費用の記録が必ず伴う。ファイルの台帳では、1 本の書き込みの待ち行列・決まった書く順・最後に書く 1 行をコミット点にする約束・費用上限の「集計してから仮押さえ」を 1 つの操作にする仕掛けを、全部自前で組む必要があった。SQLite のトランザクションはこれらをそのまま与えるので、自前の仕掛けが要らない。
2. **案件をまたぐ一覧がクエリで済む。** ホームの「確認待ち」「進行中」「自動で開始した依頼」のように、画面は案件をまたいで一覧を出す。ファイルの台帳では、そのたびに全部を読み直して畳むことになる。データベースなら一覧は 1 本のクエリになる。
3. **「台帳とフォルダで全部が分かる」は保てる。** 状態の置き場をデータベース 1 つに決め、人が開いて読む文書は案件フォルダに残す。どこを見れば何が分かるかは変わらない。遷移の出来事は追記専用の表に 1 遷移 1 行で残すので、何がいつどう変わったかも後から追える。

データベースのファイルは `checks/` と同じく作り手のセッションから読めない場所に置く（実装設計書 8.3）。表の定義とライブラリの選び方は実装設計書 9 章。

### 13.4 なぜ claude-org の道具を持ち込まないか

worktree は複数の作り手が同じコードに触るための隔離で、文書は 1 案件 1 作り手で版を積むので要らない。PR と CI は合流前の検査と承認で、libretto では判定とゲート②③がその位置にあり、合流先が無い。伝送層とペイン運用は、ホスト 1 本が役割をセッションとして起こす形では要らない。

### 13.6 検品観点の妥当性

libretto の検品観点は 3 つの考えを重ねたものである。(1) 別系統の読み手が成果を読み、重大度を付ける（参考: claude-org の Codex ゲート）。(2) 読み手は渡された中身の要約を記録に残し、重大度と根拠を付け、往復の予算を持つ（参考: rondo の独立した読み手）。(3) 物差しを作る側と作る役を切り離し、人は入口で物差しを承認し、判定は機械的に流す（参考: factory）。読む対象をコードから文書に替え、確認項目を文書の失敗（声・事実・自然さ・適合・形式）に差し替えた。機械判定が先に立つ理由と、別系統を確認項目の下書き（Codex）と命題の判定（Jev）に置いて Claude に残る判定を表示で補う理由は 5.6 に書いた（Q3 = a）。
