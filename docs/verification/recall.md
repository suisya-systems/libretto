# 受け入れ (4): 自動検出の見落としを測る

設計書 3.5 の受け入れ確認 (4)（推測の拾い漏れ）を測る手順（[`implementation.md` 6.9 (8)(9)](../implementation.md)）。本物の Gmail・Slack で、オーナーが使いながら 30 日分をためて測る。テスト（`npm run verify`）は偽の Google・Slack で回り、ここは測らない。

## 何を数えるか

- **分母**: 自動検出の範囲の中で、本人がラベル `libretto` を付けたメール・リアクション :memo: を付けた Slack の投稿（1 件につき 1 回）。範囲の中 = 自動検出が動いている（設定の「1 日に判断する件数の上限」が 0 でない）かつ、Gmail は受信箱のメイン・本人が To / Cc・本人が始めたスレッドでない・設定の日数の中・除外していない差出人、Slack は DM でない・設定で選んだチャンネルか本人宛てのメンション・7 日の中・除外していないチャンネル。
- **分子**: そのうち、ラベル・リアクションより前に自動検出が候補にしていたもの（見送った・進めたものを含む）。
- 自動検出が「依頼ではない」としたもの、1 日の上限や失敗で見られなかったものは、見落としに数える。

数えた結果は台帳（`candidate_events` の `recall_sample`）に残り、設定の「自動検出」の欄に直近 30 日の割合が出る。

## 手順

1. 設定の「自動検出」で範囲を決める（初期設定: メールは受信箱のメインの直近 7 日、Slack はあなた宛てのメンション。チャンネルを選べば足す）。Slack のメンションを測るには、Slack アプリに `search:read` が要る（[`implementation.md` 6.6 (9)](../implementation.md)）。
2. ふだんどおり使い、文書づくりを頼まれたメール・投稿にはラベル・リアクションを付ける（自動検出の候補に出ていても付ける）。
3. 30 日たったら、ホストを止めずに次を流す。データベースを読むだけで、何も書かず、モデルも外部も呼ばない。

   ```
   npm run measure -- recall
   ```

   出力: 直近 30 日の標本の数と、先に見つけていた割合。見落とした候補の id（Gmail はスレッドを開くリンク、件名は候補が残っているときだけ）。

4. 割合が **9 割を下回ったら**、見落とした候補を開いて、前さばき（`host/src/intake/classify.ts` の `prefilter`）と分類の文（`CLASSIFY_INSTRUCTION`）を**緩める**向きに直す。精度を上げる（誤検出を減らす）向きには直さない（設計書 3.5 (4)。誤検出は見送りと除外で捌く）。
